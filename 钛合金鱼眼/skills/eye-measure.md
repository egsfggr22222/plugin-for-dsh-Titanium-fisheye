# 钛合金鱼眼 —— 看图、量坐标、别被骗

`eye` 工具给你一张**真实分辨率**的截图。但从文件到你眼睛，中间有一次你看不见的压缩。

## 一、你看到的不是原图

同一张图：

| 环节 | 尺寸 |
|---|---|
| `eye` 生成的文件 | 工具返回的 `width` × `height` |
| 你实际收到的预览 | **通常更小，而且大小可能变** |

**压缩比不是固定的。** DSH 的投递策略可能随版本调整，今天 0.89，明天可能是 0.75 或 1.0。

所以：**不要背任何比例数字，每次自己确认。**

## 二、先拿到两个确定的数

| 数 | 从哪来 |
|---|---|
| **文件真实尺寸** | `eye` 返回的 `width` / `height` |
| **桌面真实尺寸** | `eye` 返回的 `screen.w` / `screen.h` |

这两个是工具量出来的，可信。

**你不知道的是**：自己看到的预览有多大。这一点必须用间接办法确认。

## 三、三种做法，按可靠性排序

### 做法 A：根本不靠眼睛（最可靠）

```
1. eye { action: "desktop" }          干净桌面，不被窗口遮挡
2. 用程序（Python + PIL）找目标边界     输出精确 bbox
3. pencil draw 用程序给的坐标          程序算的是真实像素，无需任何换算
4. eye { action: "screen" } + 程序检测  核对标记实际落在哪
```

**程序算出的坐标就是真实坐标。** 全程不经过你的视觉，压缩比是多少都无所谓。

这是首选。眼睛只用来「判断这是什么」，不用来「确定它在哪」。

### 做法 B：申报 view，让工具换算

如果不得不在图上目测：

```json
pencil { action: "draw", view: { "w": <你量坐标那张图的宽>, "h": <高> }, items: [...] }
```

**难点**：你得知道「我看到的图多大」。如果拿不准，用做法 C 先测出来。

### 做法 C：用一对已知点反推

在图里画面上找两个**真实位置已知**的点（比如屏幕四角、某个已知控件边缘），量出它们在图上的距离，和真实距离一比：

```
比例 = 真实距离 / 图上距离
```

这个比例就是你的视图缩放比，之后所有目测坐标都乘它。

**每次会话都要重新测**，因为比例可能变。

## 四、三个必踩的坑

### 坑 1：拿缩略图当原图

看到一张预览，默认它就是工具给的尺寸，坐标直接填进去 → 整体缩小、向左上偏。

**正确做法**：先确认你的视图尺寸，再换算，或者干脆用做法 A。

### 坑 2：把文件名标签当图标

Windows 桌面图标 = **上面是图标，下面是文件名**，标签比图标低一段距离。

按标签位置去圈 → **圈到了图标底部的空白**。

**正确做法**：圈图标本体。图标和标签是两回事。

### 坑 3：用「landed at」冒充「量对了」

`pencil draw` 返回的 `landed at` 只证明**画板忠实地画在了你要求的坐标**。

它**不证明你要求的坐标是对的**。目标量错了，landed 再准也没用。

**正确的自检**：画完截图，用像素检测找出标记实际落在哪，再和目标位置比对。

## 五、自检的四个问题

画完一张，按顺序问自己：

1. **我看的图多大？** 和 `eye` 返回的 `width` 一致吗？
2. **目标位置是量出来的还是估出来的？** 估的就重做，用程序量。
3. **`landed at` 和我请求的一致吗？** 一致只说明画板没歪。
4. **标记实际落在目标上吗？** 用像素检测确认，这才是真答案。

第 4 条是唯一能证明「画对了」的检查。

## 六、一句话

> **能用程序量的，绝不靠眼睛估。**
>
> 眼睛只用来「判断这是什么」，不用来「确定它在哪」。
>
> 任何比例、尺寸，都要**当场确认**，不要凭记忆。
